# E-Whatsapp Automation Tool — requirements for the EPOS integration

**For:** the developers of the E-Whatsapp Automation Tool (wa.esystematics.com)
**From:** the EPOS team · **Version:** 1 · **Date:** 2026-10-24
**Supersedes:** Part B of "EPOS ⇄ E-Whatsapp Automation Tool integration spec v1" (the hand-configured *API Call* approach). Part A of that spec (your API for EPOS) stays as is.

## 1. What we want to achieve
An EPOS admin presses **one button** (*Link automation*) inside EPOS. From then on, in the tool:
- "E-POS" appears as a ready-made source in the automation builder and in the inbox.
- The admin of the tool picks *what to ask EPOS* from a list (products, stock, orders, a customer's own profile, ledger, business hours …), instead of typing URLs, headers, keys or webhooks.
- A customer or supplier chatting on WhatsApp can ask for their own profile, records and ledger, and get the ledger as a PDF for a date range they choose.
- Everything EPOS exposes to the tool is read-only, except one deliberate action: EPOS sending the person their own ledger PDF.
- The tool and EPOS stay in sync without manual work: the list of things the tool can ask is published by EPOS and re-read by the tool.
Nobody enters a URL, an API key, a header or a webhook by hand — on either side.

## 2. Who does what
EPOS: holds data; creates read-only key; decides which questions are shareable; publishes the manifest; registers itself via the Integrations API; registers its webhook (already done); calls /messages/send.
Tool: never stores EPOS data (cache only, §7); stores key encrypted; fetches+caches manifest; builds flow/inbox UI from manifest (R4,R5); calls EPOS during a chat with the right phone number (R3); builds Integrations API (R1).

## 3. Flow
1 Admin clicks Link automation in EPOS. 2 EPOS POST /api/v1/integrations {base_url,key,manifest_url,manifest_version} (R1). 3 Tool GET {manifest_url} Bearer key (R2). 4 Tool shows "E-POS" in builder + inbox (R4,R5). 5 Customer writes -> node "E-POS: <question>" -> Tool GET/POST {EPOS endpoint}?phone=<sender> (R3). 6 EPOS toggles -> PUT /api/v1/integrations/{id} -> re-fetch (R2). 7 "Send my ledger" -> tool calls EPOS action -> EPOS renders PDF and sends via POST /api/v1/messages/send multipart document (R6).

## 4. Requirements (MUST/SHOULD/MAY literal)
R1 Integrations API, `/api/v1`, Bearer ability `integrations:write`: POST /integrations (idempotent on type+base_url), GET list/one (never returns key), PUT /{id} (key, base_url, manifest_version, name), DELETE /{id} (delete key + cached manifest), POST /{id}/check.
 Create body {type:"epos",name,base_url,manifest_url,key,manifest_version}. 201 new / 200 updated {id,status:"connected",capabilities:9,manifest_version}; 422 {error:"manifest_unreachable",detail}; 403 lacking ability; 422 field-level validation.
 AC: key encrypted at rest, never returned/logged/sent to browser; no duplicates; type enum (epos now); several integrations per workspace MAY; bad key rejected at create time (manifest fetched before saving).
R2 Manifest fetcher/cache: GET {manifest_url} Bearer key, Accept json, cached per integration. Refresh on create/PUT/check; when any EPOS response header X-Epos-Manifest-Version differs from cached; when builder/inbox panel opens and cache > 10 min. Health: GET /api/whatsapp/v1/ping at most 1/min while in use; after 3 consecutive failures mark `unreachable`: banner, stop live calls (flows take "no data" branch immediately), retry backoff 1 -> 5 -> 30 min, auto recovery.
 AC: capability switched off disappears within one refresh without deploy; flows using a vanished capability take "no data" branch and author sees warning "this EPOS question is no longer available"; manifest validated against §5, invalid capability skipped (not whole manifest) and reported on status page.
R3 Executor: server-side only; headers Authorization Bearer, Accept json, X-Request-Id (also in logs). Params bound by `from`: sender_phone = contact's WhatsApp number E.164, author MUST NOT override/map another value, no message-text value may reach it; chat_answer = author maps earlier answer ({{answer.period}}); fixed = constant. Timeout 5 s total, no redirects, TLS verify. Non-2xx/timeout/invalid JSON/>100 KB => "no data" branch, never raw error to customer. `found:false` in 2xx = normal "not found" branch. Result stored in flow variable (default `epos`) usable as {{epos.customer.name}}, {{#each epos.orders}}, conditions. SSRF guard: resolve DNS, refuse private/loopback/link-local/metadata (10/8, 172.16/12, 192.168/16, 127/8, 169.254/16, ::1, fc00::/7), re-check per request; allow_private_hosts dev switch off by default. Circuit breaker per integration. Rate limit outgoing 60/min per integration. Actions (kind action) are POST JSON with Idempotency-Key stable per flow-run+node, never auto-retried after timeout; queries are GET and MAY retry once.
 AC: unit test flow author cannot change sender_phone (UI and API); test 6 s EPOS response -> "no data" at ~5 s; test base_url http://169.254.169.254/ refused.
R4 Builder "E-POS" node: shown when workspace has active integration; capability dropdown from manifest (label.en/label.ur fallback en) grouped by `group`; params rendered by type (text, number, date, choice, phone); sender_phone params auto-bound read-only ("Customer's WhatsApp number"); variable picker offers outputs[] paths with types; default reply text from summary_template; two exits found / not-found-or-no-data; RTL for Urdu; no raw URL/header/key fields.
 AC: admin builds "ask period -> send my ledger PDF" using only dropdowns and the manifest `choice` list.
R5 Inbox panel "E-POS" (only when integration active and contact number resolves): profile (name, type, balance + receivable/payable), last 5 records with status, Send ledger PDF button with period picker (same choice list + custom dates). Read-only for agent except ledger send. Lazy load, "EPOS not reachable" without blocking inbox, hidden for found:false ("Not an EPOS customer/supplier"). AC: opening a conversation never waits on EPOS (async, 5 s cap).
R6 Ledger PDF action: EPOS renders PDF and sends itself via existing POST /api/v1/messages/send multipart. Tool must: 1 confirm in writing + keep supporting multipart document upload up to 20 MB with filename and caption (tell them if not supported on Cloud-API path); 2 message lands in same conversation as the contact and marked sent via API; 3 flow node for this capability is an action returning {"found":true,"ok":true,"message_id":123} or {"found":true,"ok":false,"reason":"rate_limited"|"window_closed"|"no_data"}; exits sent / not sent, author writes confirmation text; 4 expose `reason` as a variable. EPOS-side rules: max 366 days, max 5 ledger sends/hour/number, custom needs from and to.
R7 Webhooks: confirm in writing 1 which signature header+scheme is actually sent today (X-Webhook-Signature t=<unix>,v1=<hmac> vs X-Signature-256 sha256=<hmac>); 2 is `message.failed` a valid subscribable event (an earlier instance rejected with 422 "selected events.N is invalid"); same for delivered/read (nice to have).
R8 Security/privacy: key secret (encrypted, redacted in logs, rotatable, deleted on unlink); do not store EPOS responses beyond short cache, no cross-conversation caching of customer-specific responses; per-conversation vars live only for flow run; logs mask phones (+9233•••6444), no response bodies; identity = WhatsApp number of conversation contact; group chats and contacts without verified number MUST NOT trigger sender_phone capabilities; only users with permission to edit automations add E-POS nodes; only workspace admins see integration status; never show base_url host or key to non-admins.
R9 Non-functional: <= 50 ms own overhead per EPOS call; manifest <= 200 KB; responses <= 100 KB; all UI strings English + Urdu; audit trail per call: integration id, capability key, status, latency, found — nothing else.

## 5. Manifest schema
manifest_version, business{name,timezone,currency,language_default}, capabilities[]{key, kind query|action, group, label{en,ur}, description{en}, method, path, params[]{name,type text|number|date|choice|phone, from sender_phone|chat_answer|fixed, optional, required_if{param:value}, default, choices[]{value,label{en,ur}}}, outputs[]{path (dotted, * for list items), type text|number|boolean|date|datetime}, summary_template optional}. Unknown fields ignored. manifest_version changes whenever any capability changes. Every EPOS response carries X-Epos-Manifest-Version. (Full JSON example for contact.ledger_pdf was in the paste.)

## 6. Capabilities EPOS will publish
All HTTP 200 JSON with `found` bool; only auth failure is 401 JSON. contact.profile (query), contact.records (query, max 10), contact.ledger (query), contact.ledger_pdf (action), orders.status (query), products.search / products.get (query), services.list (query), business.hours (query). Example profile and ledger answers were in the paste.

## 7. Caching
Manifest cached per integration. Query responses MAY be cached 60 s only for non-person-specific capabilities (products.*, services.list, business.hours). Never cache anything carrying sender_phone (contact.*, orders.*).

## 8. Acceptance tests (run together)
1 create -> 201, builder shows E-POS with all capabilities in English and Urdu. 2 wrong key -> 422 manifest_unreachable, nothing saved. 3 switch products.* off in EPOS -> gone within one refresh; existing node takes "no data" branch + author warning. 4 customer number -> profile; unknown -> found:false -> author's not-found text. 5 supplier number -> balance_type payable. 6 send ledger last_month -> PDF in same conversation within 30 s, inbox shows outgoing document, 6th within hour -> reason rate_limited. 7 custom 400-day range -> reason range_too_long. 8 author maps typed phone into phone param -> blocked. 9 EPOS 6 s -> "no data" at ~5 s. 10 base_url private IP -> refused. 11 rotate key via PUT -> calls keep working; key never in any tool log. 12 unlink -> integration, key, cache gone; flows show "E-POS is not linked".
